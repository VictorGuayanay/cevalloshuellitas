## 1. System Overview

**Huellitas** is a Flutter mobile app (Material 3, SDK ^3.8.0, Provider state management)
backed by Supabase (Postgres + Storage + Realtime + 2 Edge Functions) and Firebase
Cloud Messaging (push only — Firebase was stripped of everything else after the SENSO
module migrated from Firestore to Supabase).

Layered architecture:

```
lib/
├── supabase_config.dart        # URL + anon key + Google Web Client ID (hardcoded)
├── main.dart                   # init (Firebase→Supabase→LocalNotif→FCM), providers, routes
├── core/app_colors.dart
├── data/models/                # 8 models (Usuario, Mascota, Senso, Veterinario, Noticia, Notificacion, SolicitudRol, Productor)
├── data/services/              # 10 services (auth, mascota, senso, productor, veterinario, noticia, solicitud_rol, admin, fcm, notificacion_local)
├── domain/controllers/         # 7 ChangeNotifiers (auth, mascota, notificacion, veterinario, noticia, admin, productor)
└── presentation/
    ├── screens/                # login/ (2), usuario/ (6), admin/ (1 + 4 tabs), splash
    └── widgets/                # 10 widgets (senso_sheet, mascota_form_sheet, carnet QR, etc.)
supabase/
├── migrations/add_fcm_token.sql   # ← the ONLY migration file in the repo
└── functions/
    ├── notify-mascota-perdida/index.ts   # broadcast FCM when a pet is lost
    └── notificar-adopcion/index.ts       # FCM to owner on adoption request (webhook-triggered)
test/widget_test.dart           # default Flutter counter smoke test (BROKEN — app is not a counter)
```

**Startup flow** (`lib/main.dart`): Firebase.initializeApp (best-effort) →
`Supabase.initialize` → local notifications → FCM init → providers → `home:` is a
`Consumer<AuthController>`: splash while `isInitializing`, `AdminScreen` if
`rol == 'administrador'`, `HomeScreen` otherwise, `LoginScreen` when no session.
Session restore runs at provider creation (`AuthController()..tryRestoreSession()`).

### 2.2 Issues found (login module — prioritized)

**P0 — Correctness / Security**

1. **No `onAuthStateChange` subscription.** UI state is a snapshot taken at build time.
   If the session expires/revoked/token refresh fails while the user is in the app, the
   app keeps showing `HomeScreen`/`AdminScreen` with a dead session and every query starts
   failing with 401s until restart. Conversely, after OTP recovery creates a temporary
   session, routing can desync (recovery screen pops back to `LoginScreen` even though a
   session now exists). Fix: global listener in `AuthController` reacting to
   `SIGNED_IN / SIGNED_OUT / TOKEN_REFRESHED / USER_UPDATED / USER_REMOVED`.
2. **Privilege escalation depends entirely on unverified RLS.**
   `AuthService.signUp(rol: ...)` accepts any rol (UI limits to `usuario`, API does not),
   `AuthService.updateUserRol()` and `AdminService.cambiarRolUsuario()` UPDATE
   `usuarios.usua_rol` from the anon-authenticated client, and `admin_service.dart` reads
   every table from the client. If RLS does not restrict `usua_rol` writes to
   service-role/admin, **any user can promote themselves to `administrador`** via a raw
   PostgREST call. RLS policies are **not in the repo** (only migration is
   `supabase/migrations/add_fcm_token.sql`) → cannot verify from code. Highest-risk item.
3. **Non-atomic signup → unrecoverable "login loop".**
   `signUp()` = 2 independent calls (Auth account, then `usuarios` INSERT). If step 2 fails
   (RLS, network, constraint) the Auth account exists but has no profile; the next login
   call `getUserProfile().single()` throws → generic `'Error inesperado: …'` and the user
   can never enter, with no self-service repair. Same end-state for Google first-time
   INSERT failure. Recommended direction: create the profile server-side (DB trigger on
   `auth.users` or an Edge Function) instead of client INSERT.
4. **Email-confirmation bounce (conditional on project settings).**
   With "Confirm email" enabled, `auth.signUp` returns a user **without a session**;
   `AuthController.register()` still reports success and navigates to `/home`, but
   `isAuthenticated` is false → user lands back on `LoginScreen` and sign-in fails with
   "Debes confirmar tu correo" and **no resend-confirmation action exists anywhere**.
   Whether confirmation is enabled is a project setting — must be checked in Supabase
   Dashboard → Auth → Providers → Email.

**P1 — Robustness / UX**

5. **Recovery OTP flow depends on a customized email template.** The UI demands a 6-digit
   code and calls `verifyOTP(OtpType.recovery)`. This only works if the Recovery email
   template contains `{{ .Token }}`; Supabase's default template is link-only
   (verified against Supabase docs/discussions). Not verifiable from the repo — if the
   template wasn't customized, password recovery is silently broken for real users.
   Also: rate-limit errors from `resetPasswordForEmail` are swallowed into a generic
   message, and there is no cooldown/resend timer (user can hammer "Enviar código").
6. **Incomplete error mapping.** `_mapAuthError` misses rate-limit/lockout
   ("For security purposes, you have X attempts", `over_email_send_rate_limit`),
   network failures, and OAuth-specific errors → raw English exception text leaks to the
   UI (`'Error inesperado: $e'` in `auth_controller.dart` login()).
7. **Stale error banner.** `_errorMessage` is never cleared at the *start* of a new
   operation; after a failed attempt a later successful call (or Google cancel path) can
   leave the previous error visible on the login form.
8. **Google UX quirks.** `googleSignIn.signOut()` is forced before *every* attempt
   (deliberate, to avoid cached tokens, but always re-shows the account picker and tears
   down Google session state); Google profile photo and phone are never persisted to
   `usuarios`; "cancelado" detection is done via string matching
   (`msg.contains('cancelado')`).
9. **Post-recovery session oddity.** `verifyOTP(recovery)` creates a session; the app then
   pops back to the Login screen (still in the nav stack) with `currentUser == null`.
   Works, but confusing: user must log in again although already authenticated.
10. **Logout cleanup asymmetry.** Perfil logout clears `MascotaController` only;
    admin logout clears nothing; `NotificacionController` Realtime subscription and
    `ProductorController` data survive logout. FCM token is cleared (good).

**P2 — Polish**

11. Splash always waits 1200 ms even when restore is instant.
12. Password policy is Supabase default (≥6) — no strength meter, no session
    invalidation of other devices after password change (Supabase does sign out other
    sessions by default on password update — behavior to confirm), no biometric/remember.
13. `login_screen.dart`/`register_screen.dart` are very large single files
    (963/459 lines) mixing painters + recovery flow; the recovery screen is a private
    class inside `login_screen.dart` (hard to test — relevant because TDD is mandated).

### 2.3 Session & role routing map

- `main.dart:158` — `rol == 'administrador'` → `AdminScreen`, else `HomeScreen`

## 5. Business-Core Gap Analysis — Provincial SENSO (consumo / hogar / venta)

### What exists today (supports the domain)
- Per-producer census form with production type (menores/mayores), species, animal
  count, feeding type, and **destination** — `lib/presentation/widgets/senso_sheet.dart`.
- Storage/listing/deletion of a producer's own census records
  (`lib/data/services/senso_service.dart`, profile section `_SensoCensoSection`).
- Producer self-declaration (`usua_es_productor`, `usua_tipo_animales`).
- Downstream consumption of census data: **"productores en venta"** on the
  Servicios tab and on the map (only `destinacion ∈ {venta, ambos}`).
- Appropriate-ish data model: aggregate counts per species per producer — matches a
  livestock census (censo pecuario) shape.

### Gaps vs. the required provincial SENSO

| # | Requirement | Current state | Gap severity |
|---|---|---|---|
| G1 | **(b) crianza para HOGAR** (companionship/home) | `destinacion` only allows `consumo \| venta \| amb both` — the value **`hogar` does not exist** in `senso_sheet.dart` nor in `SensoModel` labels | **High — core domain value missing** |
| G2 | **(a) consumo / (c) venta** | Present as single-choice toggle | Low (works) |
| G3 | **Provincial scope** (territorial segmentation: cantón/parroquia/sector, province-level aggregation) | No territorial column anywhere; GPS only as optional free-text `"lat,lng"` on the user; no aggregation queries/views, no admin census tab | **High** |
| G4 | **Provincial reporting / dashboards** | Admin dashboard counts users/pets/vets/news — **zero senso metrics** (no totals by species, destination, territory) | **High** |
| G5 | Census **period / edition / validity** (anual censo, vigencia) | Only `created_at`; no period, no reopen/close, no dedup (same producer can insert unlimited rows for same species) | **High** |
| G6 | **Validation workflow** by the authority (borrador → enviado → validado/rechazado) | Rows are immediately final; only delete by owner; no estado | Medium-High |
| G7 | Producer **verification** (it's an official census; `es_productor` is self-declared by any user in the profile sheet) | No approval step, no cédula validation (though `usua_cedula` exists) | Medium-High (data integrity) |
| G8 | Species **catalog consistency** (provincial totals require normalized species names) | Free-text `especie` with UI suggestion chips (`'Bovinos (vacas)'`, etc.) — inconsistent values will break aggregation | Medium |
| G9 | Link census ↔ individual animals (mascotas) / herds | `sensos` and `mascotas` are completely unrelated tables | Medium (depends on requirements) |
| G10 | **Sensors / telemetry** | No sensor tables at all (explicitly checked) | Info — out of scope unless requested |
| G11 | Edit census record | `SensoService` has create/list/delete but **no update** | Medium |
| G12 | Adoptions module (adjacent) | Server-side table + edge fn exist; **no client module**; `MascotaService.obtenerMascotasParaAdopcion()` is defined but never called | Medium (decide build-vs-remove) |

### Partially covered / inconsistent bits
- `usuarios.usua_tipo_animales` (`menores/mayores/ambos`) duplicates `sensos.produccion`
  at user level — two sources of truth.
- `masc_estado` values mix casing (`'Disponible'` vs `'perdido'` vs `'para adoptar'`);
  all comparisons are `toLowerCase()` defensively.
- Productor map query does `.eq('usuarios.usua_es_productor', true)` **after** an
  `usuarios!inner` join — works, but shows census data of *any* user to *any* logged-in
  user (privacy posture of the census is "public to all users"; needs confirmation).

## 6. Prioritized Improvement Opportunities

### P0 — Login / Auth first (as requested)
1. **Verify & harden RLS/role enforcement** (export current policies, then: block
   client writes to `usua_rol` except via admin-only path; make admin queries
   server-side or policy-guarded). *Enabler: cannot start without the export (see D2).*
2. **Global auth-state listener** (`onAuthStateChange`) → reactive routing, session
   expiry handling, post-recovery navigation fix.
3. **Atomic profile creation** (DB trigger on `auth.users` insert, or Edge Function) to
   eliminate the orphan-account login loop; add a self-diagnosis screen/action when the
   profile row is missing.
4. **Recovery flow verification & completion**: confirm `{{ .Token }}` in recovery
   template; map rate-limit errors; resend cooldown; "confirm email" resend action.
5. **Error-mapping + stale-error cleanup** in `AuthController` (clear `_errorMessage` at
   operation start; add rate-limit/network/OAuth mappings; stop leaking raw exceptions).
6. **Migrate both Edge Functions from FCM Legacy API to HTTP v1** (service account
   secret) — today broadcast pushes almost certainly fail silently.

### P1 — Data & SENSO core
7. Schema-as-code baseline: `supabase/config.toml` + baseline migration (+ RLS) so the
   DB lives in the repo.
8. SENSO: add `hogar` destination (see D6), add territorial fields, census period,
   status workflow, update method, species catalog (lookup table or constrained list).
9. Admin SENSO module: census dashboard/tables/export (currently absent).
10. Remove/repair dead code: `send-push-notification` reference,
    `obtenerMascotasParaAdopcion`, `cargarTodasLasMascotas` vet view (wire it or drop),
    broken `test/widget_test.dart`.

### P2 — UX / hygiene
11. Splash min-delay, Google photo sync, logout cleanup symmetry, split mega-screens,
    persist/dedupe in-app notifications, unify `masc_estado` casing.
12. `google_sign_in` 6.x is legacy (v7+ has a different API) — upgrade decision (D8).
13. Test baseline (D9): zero real tests today; TDD is mandated by config.

  single change risks violating scope limits and TDD overhead.

  meaningful tests require refactoring first (or service/controller-level tests only).

  until replaced.
